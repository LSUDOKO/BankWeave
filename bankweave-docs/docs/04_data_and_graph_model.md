# 04 — Data & Graph Model

## 4.1 Source data: IBM synthetic AML transactions

- Kaggle: `ealtman2019/ibm-transactions-for-anti-money-laundering-aml` (also linked from
  github.com/IBM/AML-Data). Fully synthetic → allowed by the hackathon data rule.
- Generated by IBM's AMLworld simulator: individuals, companies and banks; criminals launder
  through **placement → layering → integration**. Every transaction carries a laundering label.
- Variants: `HI-*` (higher illicit ratio) and `LI-*` (lower), sizes Small / Medium / Large.
  **Use HI-Small** for development and evaluation.
- Files per variant:
  - `HI-Small_Trans.csv` — transactions
  - `HI-Small_Patterns.txt` — laundering attempts grouped by one of **8 patterns**
    (fan-out, fan-in, cycle, random, bipartite, stack, scatter-gather, gather-scatter).
    Not all laundering follows these patterns.

### Expected CSV columns (VERIFY against the header)

```
Timestamp, From Bank, Account, To Bank, Account(.1), Amount Received, Receiving Currency,
Amount Paid, Payment Currency, Payment Format, Is Laundering
```

The two "Account" columns usually load as `Account` and `Account.1` in pandas. **Read the real
header first** and adapt the loader.

### Expected patterns file format (VERIFY)

```
BEGIN LAUNDERING ATTEMPT - FAN-OUT
<transaction row>
<transaction row>
END LAUNDERING ATTEMPT - FAN-OUT
```

Parse each block into a `LaunderingAttempt {id, pattern}` with its transaction rows. This is
**evaluation ground truth only** — never visible to agents or detectors.

### Stats from the SPNSA paper (preprocessed, largest weakly connected component)

| Dataset | Nodes | Edges | Illicit nodes | Illicit ratio |
|---|---|---|---|---|
| HI-Small | 372,091 | 874,017 | 6,342 | 1.70% |
| LI-Small | 504,391 | 1,184,998 | 5,285 | 1.04% |
| HI-Medium | 1,611,244 | 4,015,935 | 41,774 | 2.59% |

(Paper notes 99.6% of illicit nodes sit in the largest WCC; an account is "illicit" if it is an
endpoint of ≥1 laundering transaction.)

## 4.2 Bank split (the core idea)

The dataset already has a **bank ID per account**. Use it directly:

- Pick the **top N banks** by transaction volume (N = 3–5 for the demo; configurable).
- `bank_<id>` graph = all accounts at that bank + all transactions where **at least one side**
  is at that bank. The counterparty at another bank appears as a stub `ExternalAccount`
  (bank only sees "money went to an account at bank X").
- `consortium` graph = all accounts across the selected banks, linked by full transactions.
  Account identifiers are **hashed** (`sha256(bank|account|salt)`) to model privacy-preserving
  sharing. Synthetic identity attributes (devices, addresses) are hashed the same way.
- Accounts at banks outside the selection collapse into one `OtherBank` sink per bank (keeps
  graph small, preserves flow).

Ring demo: choose laundering attempts whose accounts span ≥2 selected banks. In a single bank
graph the attempt is fragmented; in the consortium it is one connected structure.

## 4.3 Synthetic identity layer (our own data)

IBM data has accounts, not people. Generate (seeded, reproducible) with `kyc_synth.py`:

- `Person` / `Company` owning 1..n accounts (some across banks).
- `Device`, `IP`, `Address` attributes. Inject shared attributes **for some laundering-attempt
  accounts** (realistic: mules share devices) **and for some innocent accounts** (families,
  apartment buildings, shared office) so the Skeptic has real innocent explanations.
- Name variants (`Jon Smyth` vs `John Smith`) across banks for entity-resolution demos.
- A Postgres `kyc_customers` table (customer_id, name, dob, address, onboarding_date,
  occupation, risk_rating, bank_id) for QueryWeaver.
- Mark everything synthetic in README. Keep the seed in config so judges can regenerate.

Important: the synthetic layer must not leak labels. Use a documented, randomized rule (e.g.
P(shared device | laundering attempt) = 0.4, P(shared device | innocent) = 0.03) and report it.

## 4.4 Graph layout (multigraph)

| Graph name | Contents | Who writes |
|---|---|---|
| `bank_<id>` | One bank's view | Loader, simulator |
| `consortium` | Hashed cross-bank view + alerts + cases index | Loader, agents |
| `case_<case_id>` | Investigation workspace: claims, evidence, tasks, events | Agents |
| `typology_kb` | GraphRAG-SDK knowledge graph of public typology docs | GraphRAG-SDK |
| `graphiti_mem` | Graphiti temporal facts | Graphiti |
| `procedures` | Procedural memory (investigation strategies) | Archivist |
| `eval_<run>` | Optional snapshot for eval runs | Eval runner |

Cross-graph references use string IDs (`account_hash`, `case_id`) — graphs cannot hold edges
to other graphs.

## 4.8 Loader outline (`services/loader.py`)

1. Read CSV in chunks (pandas, `dtype` set explicitly). Parse timestamps to epoch seconds.
2. Compute bank volume; pick top-N banks.
3. Build account ids; consortium uses hashed ids.
4. Batch writes with `UNWIND $rows AS r MERGE ... CREATE ...` (1–5k rows per batch).
5. Compute degrees and write `in_deg`, `out_deg`.
6. Compute `behavior_vec` per account (e.g. 16 features: log in/out counts, log in/out sums,
   mean/std amount, fraction of round amounts, fraction near reporting threshold, distinct
   counterparties in/out, mean inter-transaction gap, payment-format mix, currency mix,
   reciprocity ratio, night-time fraction) → normalize → store as `vecf32([...])`.
7. Create indexes.
8. Parse Patterns file → `eval/ground_truth.json` (NOT into any agent-visible graph).
9. Run `kyc_synth.py` → identity layer + Postgres.

Batch example:

```cypher
UNWIND $rows AS r
MERGE (s:Account {id: r.src})
MERGE (d:Account {id: r.dst})
CREATE (s)-[:TRANSFERS {txn_id: r.id, ts: r.ts, amount: r.amt_paid, amount_recv: r.amt_recv,
        cur: r.cur_paid, cur_recv: r.cur_recv, format: r.fmt, capacity: r.amt_paid}]->(d)
```

Note: FalkorDB property values must be scalars/arrays/vectors — store JSON payloads as strings.
